Safety review of the MK20 "KD replacement" branch feature/kd-replace (this worktree, HEAD 9b08871). Target: Allwinner Tina Linux armhf device (BusyBox 1.27.2 sh, kernel source of the f_hid/sunxi UDC driver at /private/tmp/tina54 if present). mk20-kbd is a new C daemon that replaces the vendor /data/KeyboardDevice (KD): it talks to the GD32 key MCU on /dev/ttyS1, draws 21 framebuffers (fb1..fb21), speaks KD's host protocol on /dev/ttyGS0 (A1A55A5E frames: JPEG canvas, JSON getInfo/setBacklight/keyStateChanged, tiles) and writes HID reports to /dev/hidg0 (PTT = Right Alt). It is opt-in (FEATURE_KBD=1, default off) and supervised by the release's mk20d.

Read: deck/kbd/ (gd32.c gd32io.c host.c panels.c screen.c jpeg.c kbd.c hid.c mk20_kbd.c, tests/), deck/firmware/release/sbin/mk20d (sections: kbd_* helpers, selftest, health, boot KBDM, `kbd)` supervisor), deck/firmware/release/share/gadget.sh (router_stop, kbd_pids/kbd_hid_holders/kbd_hid_quiesce, kbd_stop, cleanup(), setup_main, --tap), deck/firmware/release/share/mk20lib.sh (FEATURE_KBD), deck/tools/mk20-build-bins.sh, deck/KD-REPLACE-PLAN.md (§4 safety, §8 status), deck/tests/test_mk20d_kbd.py. Compare with deck/router/mk20_router.c only if useful (1.2.1 parked-fd rule, reviewed earlier).

Design decisions you should NOT re-litigate: no automatic fallback to stock KD (OTA needs only composite ECM + mk20d; a broken mk20-kbd fails selftest on probation -> loader A/B rollback; after confirm it is restarted with backoff and only WARNs); manual overrides /data/mk20/use-kd and FAT mk20-use-kd are debug-only.

Check specifically, and report only TRUE blockers:
1. GD32 safety: can ANY code path write to /dev/ttyS1 anything other than the exact knob-init frames `AA 55 SUM 06 F9 | 05 00 r r 00 00 | F5 5F` with r = 100..105 (RAM slots)? In particular can it ever emit command 0x19 (bootloader jump), the sequence 02 AA E2 78, or a 05-write with row < 100 (EEPROM)? Is the allow-list really the single choke point (gd32_tx), robust to integer/length tricks, and is the read-only mode (--no-gd32-write / kill file) airtight?
2. No two writers on ttyS1 / fb: can mk20-kbd ever run while stock KD runs (supervisor KD stop + retry, procd qt_app2, gadget.sh kd_start paths, crash/restart, boot races)? Can two mk20-kbd instances run?
3. hidg0 lifetime: is /dev/hidg0 (including parked stale fds that read "/dev/hidg0 (deleted)") never held by mk20-kbd across a UDC/configfs change (router_stop -> kbd_hid_quiesce -> kbd_stop ordering in cleanup()/setup_main, SIGUSR1 / stop-file handling in hid.c/mk20_kbd.c, fail-closed TERM/KILL)? Is the parked-fd / reopen / back-off logic free of busy loops and of the r121 cdev_init close problem?
4. Stuck modifier: realistic case where Right Alt stays held on the host (crash, teardown, replacement, EAGAIN, SIGTERM)?
5. Crash / probation rollback correctness in mk20d: restart backoff, crash-loop accounting, selftest FAIL-on-probation vs WARN-after-confirm (a confirmed release must not trigger the stock --rollback-now because of mk20-kbd), stop-file races, flock single instance, boot gating (composite only, no router and no bridge --tap in kbd mode).
6. Memory safety in untrusted input parsing: host frame parser (A1A55A5E, CRC, lengths), JSON handling, JPEG decode path (vendored stb_image JPEG-only, canvas size checks, 4:2:0/progressive, huge dimensions), tile command bounds, GD32 inbound frame parser (LEN cap). Any OOB read/write, integer overflow, unbounded allocation, or DoS that wedges the panels/host link.
7. Anything else that is a true blocker: kernel UAF, KD or Mac-link stall, boot/confirm/rollback breakage, device wedge, busy loop/CPU burn, fd/process leak that matters, security. No style nits, no "consider" items.
