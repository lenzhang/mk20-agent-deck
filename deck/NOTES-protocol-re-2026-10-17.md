# MK20 host↔T113 protocol: reverse-engineering notes (2026-10-17, 23:18–23:28 SGT)

**Input:** `mk20-research/screenkey-gh/mac_embedded_arm.elf`. This is KeyboardDevice V2.32 (unstripped, with debug info), identical to `dl/embedded_arm.elf`. It was decompiled on the box with Ghidra 11.4.2 headless; the outputs are in `/workspace/ghidra/{serial,cdc,usb,lam,xref}.c`.

**Cross-checked against:** the vendor demo `oss/OpenSourceLicenseDemo_V1.0/{mainwindow.cpp,CRC32.cpp}`, the T113 rootfs `fw/rootfs/{data,etc/init.d}`, and the imports of the macOS host app.

## Device side (KeyboardDevice)

### Which tty is opened
- `main()` calls `ConfigManager::updateUSBtype()`.
- If the config key `usbTYpe` is absent or 0, it runs `killall arecord; killall aplay; /data/setusbconfig serial`. That script creates the configfs gadget g1 with `acm.usb0`, VID:PID 1d6b:0104, product "Serial", which matches what the Mac sees.
- It then emits `set_serial_state(true)`.
- `usbTYpe == 1` instead runs `setusbconfig uac1` plus an arecord|aplay loop, and calls `set_serial_state(false)`.
- `SerialPort::device_set_serial_state(true)` → `openPort("/dev/ttyGS0")`. This is the only reference to `/dev/ttyGS0`.
- `/dev/ttyS1` (referenced from `main`) is the GD32 link (`STM32CommunicationObject`), not the host link.

### termios
`openPort`: `open(ReadWrite)`, 115200, 8 data bits, no parity, 1 stop bit, no flow control, read buffer 40960. No DTR/RTS handling.

### Recovery
- `SerialPort::errorOccurred`: for any error other than "Resource temporarily unavailable", close the port and re-run `device_set_serial_state(state)` after 1 s.
- `UsbCDCStateThread::run`: every 3 s runs `dmesg -c`. If the output contains "ERR: Operation not supported", it emits `usbCdcDeviceError`. The started()-lambda #2 then runs `cat …/usbc0@0/usb_device` and reopens the port.

### Receive path (`readyRead`)
1. `readAll()`.
2. If a file transfer is in progress (`this+0x38 > 0`), bytes go to `receive_file_data` first. On a fresh boot this counter is 0.
3. Every chunk is fed to **both** parsers:
   - `parse_cmd` (legacy, FIXEDCMDHEAD = `AA551234`).
   - `parse_cmd_new` (header `A1A55A5E`).
   There is **no handshake, FIND_DEVICE or GET_DEVICE_VERSION prerequisite, and no "connected" gate**.

### `parse_cmd_new` frame layout
- `A1 A5 5A 5E | id u32 LE | cmd u32 LE | size u32 LE | crc32(size as 4 LE bytes) u32 LE | data[size] | crc32(data) u32 LE`.
- Minimum buffer size is 20.
- If no header is found, the buffer is cleared, so a 1 MiB `'0'` preamble is harmless.

### CRC
- `Start_CheckCRC` (crc = 0xFFFFFFFF), then `Modified_CRC32_Arithmetic` with the reflected 0xEDB88320 table, then `CheckCRC_Result` (^ 0xFFFFFFFF).
- This equals zlib.crc32.

### `parse_cmd_new_t` dispatch
- **cmd 0x65 (101) = JSON:** `RemoteCommandExecutor::execute(json)` → `packet_cmd_new(sameId, 0x65, reply)` → `writeData` (QSerialPort write + flush, only if the port is open).
  - If `method == "getInfo"`, it also emits `device_protocolVersionV2_connect` and sets the app property `deviceProtocolVersion = "V2"`. This happens after the reply is sent, so it is not a gate.
- **cmd 0x64 (100) = JPEG:**
  - The JPEG is decoded to screen size. Width and height must equal the screen size and be multiples of 16.
  - On success it replies to the same id with cmd 100.
  - On failure it sends an unsolicited cmd-101 JSON with `errorString` and `requestId` (frame id 0xFFFFFFFF).

There is no separate SEND_JSON command; JSON goes via cmd 101.

## Host side (vendor apps)
- **Demo `init_port`:** 115200 8N1, no flow control, read buffer 40960. It does not set DTR/RTS.
- **Demo connect:** writes 1 MiB of `'0'`, then the getInfo frame.
- **macOS app (`ScreenKeyMacOS`, x86_64 Qt):**
  - It imports only setBaudRate, setDataBits, setParity, setStopBits, setFlowControl, setReadBufferSize, clear and flush.
  - It does not import setDataTerminalReady or setRequestToSend.
  - Its `device_ports_update` picks ports by VID:PID 1d6b:0104 or 1234:5678 that are not busy.

## Our codec
- `mk20deck/protocol.py` is **byte-identical** to the vendor implementation.
- **Golden vectors:** generated by compiling the vendor `CRC32.cpp` verbatim with `tools/golden/golden_frame.cpp`. They are pinned in `tests/test_protocol.py::test_frame_matches_vendor_golden_vectors`.
- No codec change was needed.

## Live results on the Mac (`/dev/cu.usbmodem1101`, T113 enumerated 23:13:17 SGT, no resets since)
- **23:25 SGT:** getInfo plain; after a DTR/RTS toggle; after a reopen (3 frames); and (earlier) after the 1 MiB preamble with a 15 s wait. **0 bytes received** in every case.
- **Modem lines:** DSR=0, CD=0, CTS=0, RI=0 throughout.
- **23:26:07–23:27:37 SGT:** 90 s passive listen (`tools/passive_listen.py`), no writes. 0 bytes; lines never changed.
  - Log: `~/mk20-backup/2026-10-17/passive-listen-2326.jsonl`.
  - Nobody pressed keys during this run.
- **Interpretation (strong, not yet proven):**
  - Linux f_acm raises DSR+DCD through a SERIAL_STATE notification when the gadget tty is opened (`acm_connect` from `gs_open`).
  - DSR=CD=0 therefore suggests **no process on the T113 has /dev/ttyGS0 open**.
  - Meanwhile the UI is clearly running (photo `artifacts/device-2026-10-17-2317-t113-silent.jpg`).
  - So KeyboardDevice is up, but its host link is closed. Possible causes:
    - (a) `openPort` keeps failing on EAGAIN, which is the one error that is not retried.
    - (b) Its SerialPort thread is stuck.
    - (c) `/mnt/SDCARD/lunch.sh` or the overlay customises startup. `qt_app1` runs it at boot.
    - (d) The SD card carries a different KeyboardDevice build.
- None of these can be checked from the host without a shell on the T113:
  - UART console on internal pads (3.3 V, 115200).
  - Or the SD card read on a card reader (read-only inspection of `/data`, `/mnt/SDCARD/lunch.sh`, `overlayDir`, `log.txt`).

The top strip shows a CPU/GPU/RAM widget.

### Who decides offline vs host mode
- **Default at boot:** `main()` calls `setAppProperty("deviceProtocolVersion","V1")` before `Check_Key()`.
- **Local handler:** `VideoPlayer::keyStateChanged(pressed,row,col,…)` returns immediately unless `deviceProtocolVersion == "V1"`. In V1 it looks up the theme item at (row,col) and does the following:
  - plays `soundFile`;
  - builds a command list from `controlData` / `controlDataList` (pageSwitch, keyboard_switch → `request_upload_key_s(0, keycode)`, …);
  - runs it via `FunctionRunner` / `keyStateChanged_s`;
  - typing reaches the Mac as HID through the GD32: `STM32CommunicationObject::request_upload_key` / `request_upload_string` on `/dev/ttyS1`.
- **Mode flip:** the only thing that sets `"V2"` is `parse_cmd_new_t`, on a cmd-101 `{"method":"getInfo"}` received over `A1A55A5E`.
  - After that, local typing stops and key events go to the host as `keyStateChanged` JSON (`SerialPort::device_keyState_Changed` → cmd 101, id 0xFFFFFFFF).
  - Legacy JSON `{"connect":true}` (in `device_dispose_json`, reached via the legacy `AA551234 FIXEDCMDHEAD ` parser) sets it back to `"V1"`.
- **No persistent flag:** no config file or theme key selects the mode. The only USB-related config is `usbTYpe` (0 or absent = serial ACM gadget plus `/dev/ttyGS0`; 1 = UAC1 audio gadget with the port closed). The Mac sees "Serial", so `usbTYpe` is 0.

So the "offline default mode" is simply V1, which is the boot default. It doesn't prevent host mode; getInfo would switch the device to V2 if it reached the parser.

### Legacy protocol (for reference; not used)
- **Header:** ASCII `"AA551234 FIXEDCMDHEAD "` (22 bytes), then type u32, cmd u32, size u32, crc32(data) u32, then data.
- **Device-side gate:** device-initiated legacy packets are only sent when connection state `this+0x2c == 2` (or cmd 0).
- **Abort marker:** an ASCII line `"AA551234 Abort file transfer 123455AA"` at the start of a chunk resets the file-receive state.
- **Do not send:** legacy JSON keys include `bootloader_jump` (puts the GD32 into DFU), `controlMouse`, `qmk_string`, `setDeviceName` and `wifissid`.

### New live evidence (23:4x SGT)
- **The OUT direction is drained:** the Mac wrote 8 MiB and then 16 MiB of `'0'` at about 10–11 MB/s with no write timeout.
  - In Linux u_serial, OUT requests are only queued while `/dev/ttyGS0` is open, so something on the T113 has the port open and is consuming the data.
  - This weakens the earlier inference from DSR/CD (they stay 0, so the Tina f_acm or the macOS driver probably doesn't report SERIAL_STATE).
  - One read after the 8 MiB run reported in_waiting=1020 but wasn't read. The repeat with readback (16 MiB) got 0 bytes back.
- **Abort marker then getInfo:** 0 bytes back.
- **Conclusion so far:** the device accepts our bytes but produces no reply. Since the codec matches the device parser exactly, either:
  - the consumer of ttyGS0 is not KeyboardDevice's SerialPort, or
  - its reply path (`RemoteCommandExecutor` → `writeData`) is not running.
  This needs a device-side view: the ttyS3 console (`ttyS3::askfirst:/bin/ash --login` in inittab; UART pads, 3.3 V) or a read-only image of the TF card (`log.txt`, `lunch.sh`, `overlayDir`).

## Official app test (2026-10-18, 00:00–00:08 SGT)

**Observation limits**

- So the app's UI was not observed. I used lsof, `fs_usage` (passwordless sudo) and C920 photos instead.

**Timeline** (`artifacts/official-app-2026-10-18/`)
- 00:00:12: instance 1 (pid 40322) opens `/dev/tty.usbmodem1101` and holds the lock file. Its port offset only reaches about 8 KB.
- 00:01:43: instance 2 (pid 40967) starts and instance 1 is gone. There was no crash report; who restarted it is unknown.
  - Instance 2's tty offset reached **3,989,555 B**. That is the size of the app's `static/deviceResources/data/KeyboardDevice` (**3,980,864 B**, manifest version V2.32) plus about 8.7 KB of protocol traffic. So the app pushed daemon V2.32 to the device.
- 00:03:07: instance 3 (pid 41625) starts. It never opens the port (lsof and fs_usage show no open).
- 00:03:30: the whole MK20 re-enumerates: hub, GD32, and then the T113 CDC at 00:04:04. Unclear whether that was a replug or the device rebooting.
- 00:05:5x: app quit (SIGTERM).

**Our client afterwards**
- **getInfo answers at once:** `deviceVersion "V2.32"` (was V2.31), MK20, 640×656, 20 keys plus a 428×142 subscreen at (106,0). Saved as `getinfo-0006.json`.
- **devtest --auto** (00:06:28): usb, port, getinfo, methods, files, display and via all **pass**.
  - Handshake 142 ms.
  - ACK p50/p95 15.2/17.7 ms.
  - Pattern frames at 67 fps, noise frames at 18.7 fps; suggested `max_fps` 8.
  - `fw_coord_base` = 0.
- **Backlight is 0 after the switch to host mode:** the screens were dark even though JPEG ACKs came back. After `setBacklight(80)` (acked, success) the test pattern is visible: `artifacts/device-testimage-2026-10-18-0008.jpg`.

**Implications**
- With V2.31 the device never replied on `/dev/ttyGS0`. With V2.32 plus a re-enumeration it replies at once. The root cause was device-side: the old daemon or its state. It was not our codec.
- Our client must call `setBacklight` after the handshake. Otherwise the deck stays dark in host mode.
- Once a host sends getInfo, the device is in V2 and offline typing stops until the next reboot or replug. That is expected for P0, but worth stating in the docs.

**Follow-up (2026-10-18):**
- The daemon now sends `setBacklight(cfg.backlight)` (default 80) after every handshake: the first connect, after a replug, and after a wake re-handshake.
- `devtest --headless` re-applies the backlight on its reconnect too.
- README documents that connecting leaves offline typing until the device is rebooted or replugged.
