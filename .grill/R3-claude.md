## 1. 总体评价

R2 的 P0/P1 分层做得对：Q2 已经把精确状态和审批代答移到 P1，R1 却把它们写成了 Phase-1 必过项（R2 的 C2 指出了这一点）。对 R1 的其他纠正，R3 也同意，包括：
- 拒绝前台特例（C1）；
- 切模式不强制释放 PTT（X1）；
- 不能用 CDC+B 绕过 HID 泄漏（X2）；
- 骤停后不承诺离线帧（C9）；
- 同 UID 安全边界（C14）。

D1–D14 之间没有硬矛盾，R3 同意 R2 的这一判定，不重开任何 D 项。

R3 只修改 4 项，原因都是"按原文无法安全或可行地落地"。其余 67 项照单采纳。部分采纳项附有不改变决策的"实施注记"，见 §4。

## 2. AMEND 详情（替代决策 + 补丁修订）

### A1 · F1（含 P04 第 3 段、AC3 口径）："摘要已显示 ≥300ms"无法观测

- **问题**：守护进程看不到 LCD 实际亮了什么。§7.4 的 `SHOW_JPG` 是否有显示完成回执尚未验证。按原文，"已显示"不可度量，实现方只能自行解释（比如把"已入队"当成"已显示"）。300ms 防误触规则因此可能被架空。
- **替代决策**：300ms 从"包含该请求摘要的副屏帧获得设备确认（ACK）"开始计时。如果协议没有 ACK，就用"帧发送完成 + AC1 实机测得的 P95 显示延迟"作为起点。两者都拿不到时，该设备/版本**不启用审批代答**（无法证明摘要已显示），接受/拒绝键按 AC11 置灰。其余条件不变：选中身份 + 唯一队首 requestId + 目标/映射稳定 ≥300ms；不满足就不执行，也不排队。
- **补丁修订（替换 P04 第 3 段首句）**：
  > P1 接受和拒绝均保持单击。仅当有有效选中身份和唯一队首 requestId，且包含该请求摘要（工具名与命令首行，至多 40 字）的副屏帧自设备确认（无确认时取发送完成 + 实测 P95 显示延迟）起已满 300ms，且目标/映射/请求身份稳定 ≥300ms 时生效；无法确定显示时刻的设备/版本不启用审批代答。

### A2 · F10（含 P06 第 2 段、P19 第 1 段）：VIA 失败后的唯一出路是阻塞

- **问题**：按 R2 的顺序，VIA 不可用且没有现成安全配置时，实机操作验收直接阻塞，而"不刷机、不装虚拟 HID 驱动（§6.5 方案 C）"又不能放松。整个 P0 因此只剩一个单点：VIA。macOS 自带的按设备 HID 重映射可以在不刷机、不装驱动的前提下净化输入。R2 没有考虑这条路，这是可行性缺口。
- **替代决策**：验证顺序改为：
  1. 坐标/事件；
  2. VIA 改 `KC_NO`，并确认 CDC 事件仍保留；
  3. 已验证的现有安全设备配置；
  4. **macOS 内置 `hidutil` 按设备重映射**：只匹配 VID `0x4250`/PID `0x426f`，把 19 个非 PTT 键及旋钮的 HID 用法码映射到经实测无副作用的目标码。由产品的 LaunchAgent 在设备接入时重新应用，安装/卸载遵循 F34 的可逆规则；
  5. 以上都失败，才阻塞实机操作验收。

  第 4 步的通过条件：
  - 只影响 MK20，内置键盘和其他外接键盘不受影响；
  - CDC 事件不受影响；
  - 从插入到重映射生效的窗口期内不产生副作用输入，或该窗口经实测可忽略（必须记录），否则视为未通过。

  F13–F24 仍不作为默认目标码。D8（PTT 走 VIA `KC_RALT` → 回落合成）的顺序不变，`hidutil` 不用于 PTT。
- **补丁修订（P06 第 2 段末句之前插入）**：
  > VIA 不可用时，可用 macOS 内置 hidutil 按 MK20 VID/PID 限定的重映射净化非 PTT 输入（不刷机、不装驱动、可逆卸载、接入时由产品重新应用）；仅当只影响 MK20、CDC 事件保留且接入窗口期无副作用输入时视为通过。
- P19 第 1 段的"VIA 不可用且无既有安全配置时阻塞"改为"VIA、既有安全配置与 hidutil 设备重映射均不可用时阻塞"。

### A3 · F25（含 P03 的 L4 图）：L4 槽位与 L1 空间错位，易误选目标

- **问题**：R2 的 L4 图把槽位 1–8 放在第 2–3 行，模式直选占第 1 行。L1 里 (1,1)=A1、(1,2)=A5，到了 L4 变成 (1,1)=DESK、(1,2)=槽位1。同一物理键在两页指向不同会话。用户没注意当前页时，就会选中错误的会话，再按"发送/停止"便作用到非预期目标。300ms 规则只保护 P1 审批，**保护不了 P0 的发送、停止和技能**。
- **替代决策**：L4 的槽位、命令列和底行与 L1 **逐键同位**，只把第 3 行（L1 的技能行）替换为模式直选。误按模式直选键只会切换模式，可见、可逆、不针对任何目标。其余规则（点选模式后回 L1、不可用模式置灰并显示原因、槽键单击选中/长按钉扎、失联钉扎可长按解除）沿用 R2。
- **补丁修订（替换 P03 的 L4 图）**：

```text
            列1       列2       列3       列4       列5
行1        槽位1     槽位2     槽位3     槽位4     接受
行2        槽位5     槽位6     槽位7     槽位8     拒绝
行3        DESK      HERD      TMUX      回L1      发送
行4        PTT       停止      新会话    聚焦      模式
```

  > L4 与 L1 仅第 3 行不同：L1 为四技能，L4 为三模式直选 + 回 L1；其余 16 键逐键同位同义。

### A4 · G9（含 P03 末段、P11 第 2 段、G5 口径）：默认模式下四技能会整体失效

- **问题**：Desktop 是 D1 的默认模式，而"当前线程安全预填"依赖未经验证的 AX 能力。按 R2 的写法，这个能力不成立时四技能键全部禁用。也就是说，P0 默认模式下 D5/Q4 的四技能入口实际不可用，Q4 无法兑现。R2 拒绝"暗中改成新线程"是对的，问题在"暗中"，不在"新线程"本身。
- **替代决策**：Desktop 下当前线程预填能力未验证或不可用时，技能键**明示降级**为"新线程预填"：
  - 键面常驻静态角标"＋新"，副屏常驻说明"技能将在新线程预填，不进入当前会话"；
  - 走 `codex://threads/new?path=<abs>&prompt=<text>`，只预填、绝不自动提交；
  - `path` 只取选中线程**已确认**的项目路径；路径不明、prompt 超长或编码不安全时明确失败，不猜 cwd、不截断。

  当前线程预填能力验证通过后，技能键恢复作用于选中会话，角标随之移除。herdr/tmux 不受影响。K1 effort 仍按 H5 禁用、不做类似替换：effort 改到"下一会话"后用户看不到生效对象，技能预填则在打开的新线程里直接可见、可审阅。
- **补丁修订**：
  - P03 末段"Desktop 若无法安全预填当前线程，显示不支持，不把技能键暗中改为新建线程"，改为：
    > Desktop 若无法安全预填当前线程，技能键明示降级为“新线程预填”（键面常驻“＋新”角标、副屏说明），仅预填不提交，路径取选中线程已确认的项目路径；路径不明则失败。不得无标识地改变作用对象。
  - P11 第 2 段"无此能力时禁用，不悄悄新建线程"，改为"无此能力时按 §6.2 明示降级为新线程预填，否则禁用"。
