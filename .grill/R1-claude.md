## 1. 与 D1–D14 / 已采纳 Q 的硬矛盾

下面每一条都是 PRD 内部两处文字无法同时成立。标「条件性」的，表示只在某个待验证前提不成立时才会冲突。

### H1. Q1「单击聚焦」与 §6.3 / §2.3 / §3 / D11 冲突（硬）
- §6.3 规定 Agent 键单击 = **选中**（不置前），双击 ≤350ms = 聚焦（D11）；§3 映射表沿用 Micro「默认不置前」；§2.3 和用户故事 1/2 要求「**不切窗口**」，例如浏览网页时按「接受」。
- Q1 采纳「单击聚焦该线程」后：Desktop 下的聚焦就是 `open codex://threads/<id>`，**一定会把 App 拉到前台**，用户故事 2 就不成立了；双击（D11）和「聚焦」键也变得多余。
- **建议**：Q1 只采纳前半句「槽 = Desktop 会话线程」。单击聚焦改为**条件行为**：只有 Codex App **已经在前台**时，单击才同时切换线程（类似 `⌘⇧[ ]` 的原地切换，不会抢焦点）；App 不在前台时，单击只选中，双击或聚焦键才置前。把这条写进 §6.3，作为 Desktop 的模式特例。

### H2. §6.9「Desktop 列全部线程：低 / 无公开 API」与 §6.8.1 S2「`thread/list` 官方文档」矛盾（硬，文档内部）
- 两节对同一能力给出了相反的可行性结论。
- **建议**：§6.9 改成「S2 可列线程（官方协议），**能否接入桌面正在运行的实例**未验证」，并引用 §6.8.4-2。

### H3. 动画时序与 §7.4「全局 ≤8fps」冲突（硬）
- §6.7.1（D2 的细化）要求「8 槽 150ms 左→右扫光」：8 个键在 150ms 内依次刷新，相当于约 53fps 的刷新事件。
- D4 的停止进度环要「0→100% 用时 600ms」：要看起来连续至少需要 10–15fps；如果 `SHOW_JPG` 是整画布停等（§7.4「似为」），一帧的往返时间可能就超过 100ms。
- PTT、done_unread、error 各 8fps，同时又有「多路等待全部闪烁」（§6.6）。
- **建议**：保留 D2/D4 的语义，降低它们的实现精度。扫光改为「一帧整体刷新 + 副屏 toast」；进度环改为 **4 段离散**（150ms 一格，≈6.7fps），且进度环帧的优先级高于所有状态动画（见 F14）。

### H4. 模式键底色「紫/橙/绿……与状态色不冲突」不成立（硬）
- herdr = 橙，和 `needs_input`/`needs_approval` 的琥珀撞色；tmux = 绿，和 `done_unread` 的绿撞色。模式键就在 Agent 槽旁边 (5,4)，一眼看过去会被误读成「有会话在等你」。
- **建议**：模式键使用中性深底，靠**图标 + 文字**区分模式；模式色只留在副屏徽章的细条上。去掉「与状态色不冲突」这句。

### H5. D6「K1 调节选中会话 effort」与 §6.8.2「Desktop 无公开改当前线程 effort 入口」冲突（条件性 → 实质为硬）
- Desktop 下唯一可写的是 `config.toml` 里的 `model_reasoning_effort`，这是**全局**配置，会同时影响所有 Desktop 线程以及 tmux/herdr 里的 `codex` CLI。转一次旋钮就会产生跨会话副作用，违反 D6「按选中会话解释」的语义。
- **建议**：D6 的心智模型不变，Phase-1 把 K1 的作用对象改为「**选中会话的下一次新会话 effort**」（由守护进程保存，在新会话或技能 deep link 时带上）。修改**当前线程**的 effort 后置到 P1，Desktop 还要经过 spike 确认。§2.3「转旋钮看到 effort 变化」只要求能看到变化，仍然满足。

### H6. D8（VIA `KC_RALT` 主路径）与 §6.5/§7.3 的 PTT 动画（条件性）
- 如果 PTT 键在 GD32 层直接映射成 HID 修饰键，而 T113 收不到这个键的 `keyStateChanged`（§6.5 写的是「待实机」），守护进程就不知道 PTT 被按下，`ptt_listening` 的波形和副屏「语音输入中」都做不出来。
- **建议**：明确降级规则：拿不到 CDC 事件时，PTT 键面显示**静态麦标**，副屏不提示。不要为了动画倒退到 B 路径（合成按键），因为 B 路径有卡键风险，而且 IME 未必识别（见 F7）。

### H7. §2.3 成功标准与 D1（默认 Desktop）在 S1 不成立时冲突（条件性）
- §2.3 要求「不切窗……一键批准」。但 §6.8.3 写明 S1 不成立时，Desktop 的「批准键显示『到 App 内批准』并聚焦该线程」，也就是**必须切窗**。
- §2.3 的措辞是「**至少一个模式下**」，在逻辑上留了余地，但默认模式下用户的第一印象会是「批准不了」。
- **建议**：采纳 Q2 后，在 §2.3 / §9 中明确：Phase-1 的「一键批准」验收可以由 **tmux 或 herdr** 满足；Desktop 的批准能力由 spike 结论决定，降级态的表现属于验收内容，不算缺陷。

## 2. 前沿问题（Frontier questions）

每条给出：**为何重要**、**冲突或缺失的章节**、**建议方向**。

### A. 选中模型与危险操作

**F1. 单击执行的「接受」比「拒绝」更危险，PRD 却只讨论了拒绝。**
- 为何重要：误按接受可能放行 `rm -rf`、`git push --force` 等不可逆操作；误按拒绝最多让 agent 重试。D3 让拒绝单击执行，理由是「速度优先」；接受默认也是单击执行，但 §6.3「危险操作」完全没有提到接受。
- 缺失：§6.3 危险操作、§9。
- 建议：接受**保持单击**（不推翻 D3 的精神），但增加两条硬约束：① 只有选中会话处于 `needs_approval` 时接受才生效，否则不做任何事，副屏提示「无待批准」；② 副屏必须**先显示**待批准内容（工具名 + 命令首行 ≤40 字），并且已经展示 ≥300ms，接受才生效（见 F2）。

**F2. 选中项和 Priority 重排会造成「按下时目标已变」的竞态。**
- 为何重要：§6.3 的 >8 会话策略按 Priority 重新排序；新的 `needs_approval` 出现时会把会话往前挤。用户正伸手去按 A3 时，A3 上的会话可能已经换了，于是选错会话，再按单击执行的接受或拒绝，就作用到了错误的会话上。
- 缺失：§6.3 没有规定槽位稳定性；§6.6 没有规定是否自动改变选中。
- 建议：
  - **槽位黏性**：会话一旦占了槽就不移动；Priority 只决定溢出时**谁被挤出、谁补空位**，不在槽内重排。
  - **选中不自动改变**：守护进程不会因为新的待批准会话出现而自动选中它；副屏显示 `+N waiting`，由用户自己选。
  - **冷却期**：选中会话变化后 300ms 内，或选中会话的状态刚变化后 300ms 内，接受/拒绝无效，并闪烁提示。

**F3. 单击要不要等 350ms 来区分双击？**
- 为何重要：如果为了识别双击而延迟单击的处理，每次选中都慢 350ms，手感很差。
- 缺失：§6.3。
- 建议：单击在**按下时立即**选中；如果 350ms 内出现第二击，再追加聚焦动作。单击是双击的前缀，不存在歧义。命令键没有双击语义，按下即触发；带长按语义的键（停止、模式、Agent 键钉扎）在**松开时**判定短按还是长按。

**F4. 同一会话有多个并发审批时，接受/拒绝作用于哪一个？**
- 为何重要：Codex/Claude 会并行调用工具，可能同时挂起多个 PermissionRequest。
- 缺失：§3.1、§6.3。
- 建议：每个会话维护一个 FIFO 队列，接受/拒绝只处理**队首**；副屏显示 `1/3`；键面角标显示待处理数量。不提供「全部接受」（P1 再考虑，且必须是长按）。

**F5. 拒绝的语义是「拒绝此工具」还是「拒绝并停止」？**
- 为何重要：Codex 有「拒绝并告诉它怎么改」，Claude 的 deny 会让 agent 继续尝试别的做法。用户期望可能是「不要再做了」。
- 缺失：§6.2、§6.8.2。
- 建议：拒绝 = **只拒绝该次调用**（hook 返回 deny + 固定原因「Declined via MK20」）。「拒绝并停止」= 先拒绝，再长按停止，两次显式操作，不合并成一个键。

**F6. 停止在不同工具和模式下的实际按键没有定义，存在误杀进程的风险。**
- 为何重要：tmux 下 `send-keys C-c`：对 ccai 按两次会**退出 Claude Code**；codex 的中断是 `Esc`。Desktop 下快捷键「待核」。
- 缺失：§6.7 表、§6.8.2。
- 建议：停止**按工具定义**，而不是按模式定义：ccai = `Escape`，codex TUI = `Escape`，Desktop = spike 确认的快捷键或 AX。**明确禁止发送 `C-c`**。执行前用 `capture-pane` 确认会话处于运行态，如果是 idle 就不发送任何按键。

### B. PTT = 右 Option 透传

**F7. 回落路径 B（合成右 Option）可能被 IME 完全忽略。**
- 为何重要：很多第三方 IME（包括按住右 Option 说话的那类）通过 IOHID 或 `NSEvent` 修饰键标志检测「物理右 Option」；`CGEventPost` 合成的 flagsChanged 事件可能没有右侧设备位（`NX_DEVICERALTKEYMASK`），或者被 IME 忽略。D8 把 B 当回落，但 B 可能根本无效。
- 缺失：§6.5。
- 建议：在 spike 清单 §6.8.4 中增加一项：「**合成右 Option 能否触发用户当前使用的 IME**」，免设备，在本机 5 分钟内可以验证。如果 B 无效，D8 的回落改为「PTT 不可用，提示用 Mac 自带键」，不再承诺 B 路径。

**F8. 修饰键卡住和组合键污染。**
- 为何重要：按住 PTT 期间，如果再按了另一个会发出 HID 键码的键（F13–F24 备份路径，见 F9），macOS 收到的是 `⌥+F13`，可能触发系统或应用快捷键；USB 断开、Mac 睡眠、T113 重启时，右 Option 可能停在按下状态（A 路径由 GD32 负责释放，B 路径由守护进程负责）。
- 缺失：§6.5、§8「可靠」只针对合成路径。
- 建议：① 守护进程在检测到 PTT 按住时，**屏蔽**其它键的 HID 备份发码（或在文档中声明 F13–F24 的组合键不会被应用绑定）；② B 路径：超时 30s 强制释放，并在 USB 断开、睡眠、模式切换、守护进程退出时都强制释放；③ 验收中加入「拔线 / 睡眠后不残留 Option」（见第 3 节）。

**F9. 除 PTT 外的 19 个键默认发什么 HID 码？（关键，PRD 没有写）**
- 为何重要：如果 MK20 出厂 QMK 或 ScreenKey 配置给每个键分配了字母或快捷键，按「接受」时会把字符输进当前焦点窗口（比如正在看的网页）。编码器默认很可能是**音量**，转 K1 调 effort 的同时也在改 Mac 音量。
- 缺失：§4、§6.5、§11「HID 备份 F13–F24」只有一句话。
- 建议：PRD 明确：Phase-1 用 VIA 把 **19 个键设为 `KC_NO`（或 F13–F24 备份码），两个编码器设为 `KC_NO`**，只有 PTT 设为 `KC_RALT`。这和 D8 是同一次 VIA 操作。如果 VIA 不可用，这就是**阻塞项**。

**F10. VIA 可用性本身没有验证，D8 主路径悬空。**
- 为何重要：「不刷 GD32」的前提是出厂固件启用了 VIA。如果没有启用，就需要刷 QMK，这属于 §2.2 的「高风险刷机需另批」。
- 缺失：§10.1 有提到，但没有给出失败后的决策分支。
- 建议：实机的第一项 spike 改为「VID/PID `4250:426f` 能否被 usevia.app 识别并改键」。失败时的分支：先用守护进程 + CDC 实现全部逻辑；PTT 走 B 路径（如果 F7 通过）；刷机另行审批。

### C. 动画、带宽与显示

**F11. `SHOW_JPG` 的帧成本完全未知，但 fps 表已经按 2–8fps 写死。**
- 为何重要：如果只能整画布刷新（20 键 + 副屏，可能是一张大 JPEG），一帧可能在 100–300ms 之间，那么全局实际只有 3–10fps，并且**所有键共享这个帧率**。
- 缺失：§7.3、§7.4、§8 延迟。
- 建议：把 §7.3 的 fps 列改为「**期望值**」，另加「静态降级档」：每个状态必须有一张**单帧就能区分**的静态图（颜色 + 图标 + 字），动画只是增强。实机 spike 的验收指标是：单帧往返 P50/P95、是否支持单键脏刷新。

**F12. 「selected 白边脉冲」叠加在「idle 白/浅灰呼吸」上，几乎看不出来，而且很耗帧。**
- 为何重要：选中是最常看的状态，用脉冲表达会持续占用带宽，在 idle 会话上视觉区分度又最差。
- 缺失：§3.1、§7.3。
- 建议：selected = **静态**粗白边 + 键面下方的反色名牌，不做动画。

**F13. 守护进程崩溃后，键面会一直停在最后一帧，看起来像实时状态。**
- 为何重要：琥珀「待批准」可能长时间残留，用户按接受却没有任何反应。T113 不改镜像（§2.2），设备端没有看门狗。
- 缺失：§8 可靠性。
- 建议：① 守护进程正常退出、收到 SIGTERM、Mac 进入睡眠时，先推送一帧「offline」全画布；② 副屏常驻一个心跳点（每 2s 翻转一次）；用户看到心跳不动，就知道状态已经过期；③ 崩溃导致的残帧作为已知限制写进文档。

**F14. 帧优先级没有覆盖「交互反馈」。**
- 为何重要：§7.4 的优先级顺序是 needs_approval > error > thinking，但停止进度环、拒绝后的 ✗ 闪烁、模式切换这类**对用户按键的即时回应**，如果排在状态动画后面，就会让人觉得「按了没反应」。
- 缺失：§7.4。
- 建议：帧调度优先级改为：**按键反馈 > 注意力（needs_approval/error） > 选中变化 > 其它状态动画**；按键反馈可以抢占当前帧。

**F15. 多路等待「全部闪烁」会让注意力信号失去意义。**
- 为何重要：8 个键同时闪，用户分不出先处理哪个，带宽也被占满。
- 缺失：§6.6。
- 建议：只有优先级**最高的一路**闪烁，其余等待中的会话保持静态琥珀；副屏显示 `+N waiting`。

### D. 状态模型

**F16. 缺少 `unknown` 状态（Q2 已采纳，但状态表里没有）。**
- 为何重要：`offline`（后端断开）和「后端在线但这条会话的状态拿不到」不是一回事。herdr 原生就有 `unknown`；Desktop 只有 S3/S4 时，大多数状态都属于 unknown。
- 缺失：§3.1、§7.3。
- 建议：新增 `unknown`：灰底 + 工具头像 +「?」角标，**不做动画**。语义是「会话存在，状态未知，可以聚焦去看」，与 `offline` 区分开。

**F17. 各后端状态如何映射到本产品状态，没有表。**
- 为何重要：herdr 的 `blocked` 对应 needs_input 还是 needs_approval？`working` 对应 thinking 还是 running？Desktop 的 S2 status 枚举是什么？tmux 的「粗状态」具体怎么判定？没有映射表，就没有办法验收。
- 缺失：§3.1、§6.7、§6.8.3。
- 建议：增加一张「后端原生状态 → 产品状态」矩阵（3 个模式 × hooks 有/无），无法区分的情况统一归入 `unknown`。thinking 和 running 只有在 hooks（PreToolUse/PostToolUse）存在时才拆开，否则合并显示为 running。

**F18. `done_unread` 什么时候算「已读」？**
- 为何重要：如果定义不清，绿色角标会一直挂着（用户不信任），或者刚出现就被清掉（用户错过）。
- 缺失：§3.1。
- 建议：以下任一条件满足即清除未读：① 在 MK20 上选中该会话 ≥1.5s；② 聚焦该会话；③ 后端报告已读（Desktop S2 的 readState）。只选中但很快划过不算已读。

**F19. `error` 的数据来源没有定义。**
- 为何重要：Stop hook 和 notify 不一定带错误信息；如果没有数据来源，error 状态就永远不会出现。
- 缺失：§3.1、§6.8.1。
- 建议：error 只有在后端**明确报告**时才显示：hook 的失败字段、herdr 状态、进程非零退出。不做推断。在验收中可以接受「某些模式下没有 error」。

**F20. 挂起的 hook 审批与 App 内审批互相冲突（Desktop、Claude 都适用）。**
- 为何重要：PermissionRequest hook 在等待 MK20 按键时，如果用户在 App 或 TUI 里直接批准了（如果 UI 还能显示审批），MK20 上的状态会过期；反过来，如果 hook 挂起导致 App **不显示**审批 UI，用户就只能用 MK20 批准，一旦守护进程卡住，所有会话都会卡住。
- 缺失：§6.8.2 ①、§6.8.4。
- 建议：spike 项 1 扩展为「hook 挂起期间 App UI 的表现」。设计原则：**hook 必须失败开放（fail-open）**，即守护进程不在线或连接超时（≤200ms）时，立即返回「不做决定」，交给原生 UI；等待用户按键的超时时间可配置（默认 60s），超时同样返回「不做决定」，**绝不默认返回 deny 或 allow**。

**F21. 选中会话消失时怎么办（会话结束、tmux pane 被杀、模式切换）？**
- 缺失：§6.3。
- 建议：选中项清空，命令键置灰，副屏提示「未选中」；**不要自动选中下一个会话**（理由同 F2）。

### E. 模式切换的边角情况

**F22. 不在当前模式里的会话发起了审批请求，会怎样？**
- 为何重要：当前在 tmux 模式时，Desktop 线程触发了 PermissionRequest。hooks 增强层是跨模式的（§6.7 末段），hook 挂起等待 MK20 按键，但 tmux 模式的槽位里根本没有这条会话，用户看不到，agent 就一直卡着。
- 缺失：§6.7、§6.7.1。
- 建议：① hook 只有在**会话所属模式 = 当前模式**时才挂起等待，否则立即 fail-open；② 副屏和模式键角标显示**跨模式待处理计数**（例如「DESK 1⚠」），提示用户切过去看。

**F23. 切换模式时有正在进行的交互，怎么处理？**
- 场景：切换时 PTT 正按住；停止进度环走了一半；有待批准；选中项在旧模式里。
- 缺失：§6.7.1。
- 建议：① 模式切换**不影响 PTT**（PTT 是全局的）；② 取消正在进行的长按；③ 按 Q3，每个模式保存并恢复各自的选中项和钉扎；④ 已经挂起的 hook 按 F22 处理。

**F24. 每模式独立的钉扎，如何在重启后还能找到对应会话（Q3 已采纳）？**
- 为何重要：tmux 的 `pane_id`（`%12`）在 tmux server 重启后会变；herdr 的 ID 稳定性未知；Desktop 的 threadId 是稳定的。
- 缺失：§6.3、§6.7.1 的持久化只提到「模式」。
- 建议：持久化文件保存 `{mode → [pin_key]}`，`pin_key` 按模式定义：Desktop = threadId；herdr = agent id；tmux = `session:window.pane` 名称 + 工具类型。找不到对应会话时，钉扎位显示 `unassigned` 并标注「失联」，保留 7 天。

**F25. L2/L3/L4 页的键位图没有定义。**
- 为何重要：切到 L2 后，PTT、接受、拒绝还在不在？如果不在，用户在 L2 上就批准不了。L3「技能」与 L1 的技能行重复。L4「三枚大键」的位置也没写。
- 缺失：§6.1、§6.2 只给了 L1 的键位。
- 建议：规定**全局固定键**：(5,1) 接受、(5,2) 拒绝、(1,4) PTT、(5,4) 模式在所有页的位置不变；其余 16 个键随页面变化。Phase-1 只需要 **L1 + L4**；L2/L3 推迟到 P1（采纳 Q4：四个技能已经在 L1）。

**F26. K2 旋转的双重语义「滚动摘要 / 或在 L1 微调选中槽」。**
- 缺失：§6.4。
- 建议：K2 旋转 = **在槽位间移动选中项**（高频操作，而且能和 F2 的冷却期配合）；摘要滚动推迟到 P1。K2 长按「（可选）回 L1」改为确定行为：长按 = 回到 L1。

### F. Adapter 边界（herdr / tmux / hooks）

**F27. hooks 的 session_id 怎么对应到槽位？（三种模式都需要的关联键）**
- 为何重要：Claude/Codex 的 hook payload 里有 session_id 和 cwd，但没有 tmux pane 或 herdr agent 的标识。关联不上，hooks 就无法「增强」对应的槽位。
- 缺失：§6.7「hooks 增强层」只有一句话。
- 建议：hook 脚本读取环境变量 `TMUX_PANE`、herdr 注入的 pane 变量（待查 herdr 文档）、Codex 的 thread 标识，一起上报。Desktop 模式需要 spike 确认：**hook 里的 session_id 是否等于 deep link 用的 threadId**（这一项必须加入 §6.8.4）。

**F28. 同一套 `~/.codex/hooks.json` 对 CLI 和 Desktop 都生效，如何区分来源？**
- 为何重要：tmux 里跑的 `codex` CLI 也会触发同一套 hooks。如果不区分，CLI 会话会混进 Desktop 槽位，或者被错误地挂起审批。
- 缺失：§6.8.1。
- 建议：spike 时确认 hook payload 里是否有 originator 或 client 字段。如果没有，用「是否存在 `TMUX_PANE` 或 herdr 环境变量」来判断，都没有就认为是 Desktop。

**F29. Desktop 模式下会不会出现 ccai 会话？**
- 为何重要：§6.7「Phase-1 工具过滤 ccai + codex」读起来像所有模式都包含两种工具，但 Desktop 模式只能看到 Codex 线程。
- 建议：明确写出：Desktop 模式 = **只有 codex 线程**；ccai 只出现在 herdr 和 tmux 模式。

**F30. tmux 下的接受/拒绝（`send-keys`）依赖各工具 TUI 的提示格式，存在盲打风险。**
- 为何重要：如果不确认当前是否真的在审批提示界面，直接发 `y`/`1`/Enter，就会把字符打进 agent 的 composer，甚至直接提交出去。
- 缺失：§6.7 表。
- 建议：tmux 的接受/拒绝**优先走 hook 代答**（Claude 和 Codex 都支持）；`send-keys` 只作为回落，而且发送前必须用 `capture-pane` 匹配到已知的审批提示正则，匹配不到就不执行。正则按工具版本维护。

**F31. tmux 模式下「聚焦」要激活哪个终端 App？命名约定 `ag-*` 是强制的吗？**
- 缺失：§6.7、D11「激活终端」。
- 建议：在配置中写明终端 App 的 bundle id（默认 Ghostty 或 iTerm2，需要确认用户实际在用哪个）。发现会话时，优先用命名约定；同时用 `pane_current_command`（`claude`/`node`/`codex`）自动识别作为补充，这样用户不必手动改窗格名。

**F32. herdr 在 macOS 上是否可用，没有验证（D9 的前提）。**
- 为何重要：§6.7 只核实了「Linux 构建存在」，而 D9 写的是 `brew install herdr`。如果 herdr 没有 macOS 版本，第二优先的模式就整体失效。
- 建议：把「herdr 在 macOS 上能否安装运行」作为签字前的 5 分钟核查（只读查看文档或 brew info，不安装）。如果不可用，herdr 模式降级为 P1，模式循环里显示为灰色（D2 规定「不跳过」，可以保留）。

### G. 安全

**F33. agent 能否自己批准自己？（安全，关键）**
- 为何重要：守护进程和 agent 以同一个用户身份运行。如果守护进程有本地 socket 或 HTTP 接口能「发出 allow」，agent 只需执行一条 `nc -U ...` 就能绕过人工审批。
- 缺失：§8 安全只写了「钩子最小权限」。
- 建议：**审批决定只能来自 CDC 设备上报的物理按键事件**。hook 的 IPC 只接受「请求」，决定只在同一个连接上回传；守护进程不提供任何「approve」控制接口，模拟器模式需要显式开关并在副屏标注 SIM。

**F34. 安装 hooks 会改动用户配置，需要可逆。**
- 为何重要：要修改 `~/.codex/hooks.json`、`config.toml` 里的 `notify`（还要和已有的 Computer Use notify 链式包装）、`~/.claude/settings.json`。如果装坏了，现有的工作流会受影响。
- 建议：PRD 增加一条约束：安装和卸载都是幂等的，改动前自动备份，卸载后与原文件逐字节一致；notify 链式包装在守护进程不在线时也必须执行原命令（只记录不阻塞）。

## 3. 缺失的验收标准（Missing ACs）

§9 只有「批准文档」一条，实现阶段的验收一笔带过。以下建议写入 §9.2「Phase-1 实现验收」，每一条都可以测：

| # | 验收项 | 通过条件 |
|---|--------|----------|
| AC1 | 状态延迟 | 后端事件到键面像素变化：P50 ≤500ms，P95 ≤1s（tmux + hooks，以 mock 时间戳测量） |
| AC2 | 接受/拒绝作用正确 | 在 tmux 或 herdr 中至少有一个工具（ccai 或 codex）通过 hook 代答，100 次操作中误作用于非选中会话 0 次；选中会话不在 `needs_approval` 时按下接受，后端不收到任何输入 |
| AC3 | 竞态防护 | 自动化脚本在选中变化后 0–300ms 内按接受：全部被拒绝执行并给出提示 |
| AC4 | hook 失败开放 | 守护进程被 kill 后，触发 PermissionRequest：原生 UI 在 ≤1s 内出现，不阻塞 agent |
| AC5 | 停止 | 按住 <600ms 不执行；≥600ms 只执行一次；ccai 和 codex 都只中断当前 turn，不退出进程 |
| AC6 | PTT | 按住期间 IME 处于听写态，松开后结束；拔线、Mac 睡眠、守护进程退出后，`⌥` 没有残留（用 `hidutil` 或 Key Viewer 验证） |
| AC7 | HID 净化 | 在文本框焦点下，依次按 19 个非 PTT 键并转两个旋钮：没有任何字符输入，没有音量变化 |
| AC8 | 模式切换 | 短按循环三种模式时，键面和徽章在 ≤300ms 内更新；不可用的模式显示 offline 和原因；重启后恢复上次的模式、选中项和钉扎（Q3） |
| AC9 | 跨模式提示 | 非当前模式的会话发起审批时，≤1s 内在副屏或模式键上出现计数，hook 立即 fail-open |
| AC10 | 静态可辨 | 关闭动画（0fps）时，11 种状态都能单帧区分，盲测识别率 ≥90% |
| AC11 | 降级可见 | Desktop 在 S1 不成立时：批准键显示「到 App 内批准」，按下后聚焦对应线程；副屏常驻「状态受限」标记 |
| AC12 | 过期可见 | 守护进程退出后 ≤2s，副屏心跳停止或显示 offline 帧 |
| AC13 | 自批准不可能 | 本机任何进程都无法通过守护进程接口产生 allow（安全测试脚本验证） |
| AC14 | 配置可逆 | hooks 卸载后，`~/.codex/hooks.json`、`config.toml`、`~/.claude/settings.json` 与备份 diff 为空；Computer Use 的 notify 仍然生效 |
| AC15 | 溢出 | 构造 12 个会话：钉扎的会话不被挤出；在已占槽的会话中，不在槽内重排（F2）；副屏显示 `+4` |

## 4. Desktop 可行性缺口（D1 默认模式）

§6.8.4 的 5 项 spike 方向是对的，但**不足以支撑签字**。建议补充下列项，并按「是否决定 Desktop 能否做到 P0 批准」排序：

| # | 缺口 | 为何关键 | 建议加入 §6.8.4 |
|---|------|----------|------------------|
| G1 | hook 的 session_id 是否等于 `codex://threads/<id>` 的 threadId | 如果不相等，聚焦和批准都对不上线程 | **必须加入** |
| G2 | hook 挂起期间，App 是否仍显示审批 UI；在 App 内批准后，hook 会收到什么 | 决定 F20 的冲突怎么处理，以及 fail-open 的语义 | 扩展原第 1 项 |
| G3 | hook payload 能否区分 Desktop 和 CLI 发起的会话 | F28 | 加入 |
| G4 | 用 deep link 聚焦是否会标记已读；是否切换窗口或项目 | done_unread 的语义（F18）；多窗口时的行为 | 加入 |
| G5 | `threads/new?prompt=` 的长度限制和编码；技能 prompt 模板能否带 `{cwd}` | 技能键在 Desktop 的主路径 | 加入 |
| G6 | 冷启动时如何填充槽位（hooks 只能看到守护进程启动之后的事件） | 守护进程刚启动时槽位为空；S4 解析是非稳定接口 | 加入，接受「冷启动用 S4 只读，标 unknown」 |
| G7 | App 版本漂移（26.1007.x 更新频繁） | deep link、hooks、快捷键可能随时变化 | 启动时做**能力探测**并缓存，探测失败就自动降级，副屏显示具体原因 |
| G8 | 合成右 Option 能否触发用户的 IME（F7） | D8 回落路径是否成立 | 加入（与 Desktop 无关，但同样只需要本机 GUI） |
| G9 | 发送（`Return`）会抢焦点 | 用户故事 2「浏览网页时」按发送，会把 App 拉到前台 | 不需要 spike；在 PRD 中写明「Desktop 的发送和技能会激活 App」 |
| G10 | 守护进程与 ScreenKey 是否争用同一个 CDC 端口 | 如果 ScreenKey 在后台常驻，守护进程打不开串口 | 实机 spike；PRD 要求两者互斥并提示用户退出 ScreenKey |
| G11 | 使用条款边界 | AX 自动化和 deep link 属于公开接口；`execute javascript` 已明确不采用 | 无需 spike，维持 §6.8.2 的「不采用」 |

**签字门槛建议**：G1、G2、G3 这三项决定 Desktop 的 P0 范围是「完整状态 + 批准」还是「列表 + 聚焦 + Unknown」（Q2）。不要求签字前完成，但 PRD 应写明**两种结局各自对应的 Phase-1 范围**，这样无论 spike 结果如何，PRD 都不必重新打开。

## 5. 给下一轮 GPT 的决策种子

格式：**DS 编号 — 建议决策**（依据）。可以直接改写成 D15 及以后的条目。

1. **DS1 — 槽位黏性**：会话一旦占槽就不移动，Priority 只决定溢出时的挤出和补位；守护进程永不自动改变选中项。（F2）
2. **DS2 — 接受/拒绝的生效条件**：选中会话处于 `needs_approval`，副屏已展示请求 ≥300ms，选中项和状态都已稳定 ≥300ms；不满足任一条件时不做任何事并提示。D3（拒绝单击）不变，接受同样单击执行。（F1、F2）
3. **DS3 — Q1 的细化**：槽 = Desktop 线程；单击只在 App 已在前台时原地切换线程，否则只选中；双击或聚焦键负责置前。（H1）
4. **DS4 — hook 失败开放**：连接超时 ≤200ms，等待按键超时默认 60s；任何超时或异常都返回「不做决定」，绝不默认 allow 或 deny；非当前模式的会话立即 fail-open，并显示跨模式计数。（F20、F22）
5. **DS5 — 审批只来自物理键**：守护进程不提供 approve 控制接口；模拟器需要显式开关并在副屏标注 SIM。（F33）
6. **DS6 — HID 净化**：用 VIA 一次性设置 19 键和两个编码器 = `KC_NO`（或 F13–F24），PTT = `KC_RALT`；VIA 不可用视为阻塞，进入另行审批的刷机流程。（F9、F10）
7. **DS7 — PTT 回落以 spike 结果为准**：合成右 Option 不能触发 IME 时，不提供 B 路径；PTT 键面拿不到 CDC 事件时只显示静态图标。（F7、H6）
8. **DS8 — 静态优先的视觉**：每种状态都要有可单帧区分的静态图；动画只是增强；selected 用静态边框；多路等待时只有优先级最高的一路闪烁；帧调度顺序为「按键反馈 > 注意力 > 其它」。（F11、F12、F14、F15、H3）
9. **DS9 — 修订 D2/D4 的视觉精度**：扫光改为单帧整体刷新；进度环改为 4 段离散；语义不变。（H3）
10. **DS10 — 模式键配色**：中性深底，用图标和文字区分模式；模式色只出现在副屏徽章细条上。（H4）
11. **DS11 — K1 effort 的 Phase-1 范围**：K1 调节「选中会话所属工具的下一次新会话 effort」；修改当前线程的 effort 推迟到 P1。（H5）
12. **DS12 — K2**：旋转 = 在槽位间移动选中项；短按 = 切页；长按 = 回到 L1；摘要滚动推迟到 P1。（F26）
13. **DS13 — Phase-1 只做 L1 + L4**：全局固定键为接受 (5,1)、拒绝 (5,2)、PTT (1,4)、模式 (5,4)；L2/L3 推迟到 P1。（F25，配合 Q4）
14. **DS14 — 状态表增加 `unknown`**，并新增「后端 × hooks 有/无 → 产品状态」映射矩阵；thinking 和 running 只有在有 hooks 时才拆开。（F16、F17）
15. **DS15 — 已读规则**：选中 ≥1.5s、聚焦、或后端报告已读，任一满足即清除 `done_unread`。（F18）
16. **DS16 — 停止按工具定义**：发送 `Escape`；禁止发送 `C-c`；会话 idle 时不发送任何按键。（F6）
17. **DS17 — tmux 的审批优先走 hook 代答**；`send-keys` 回落前必须用 `capture-pane` 匹配到审批提示。（F30）
18. **DS18 — 关联键**：hook 上报时附带 `TMUX_PANE`、herdr pane 变量和 thread 标识；把「hook session_id 是否等于 threadId」列为 Desktop 首项 spike。（F27、G1）
19. **DS19 — 每模式钉扎的持久化键**按模式定义（threadId / agent id / pane 名称 + 工具）；找不到会话时显示「失联」，保留 7 天。（F24、Q3）
20. **DS20 — 成功标准拆分**：§2.3 的「一键批准」可以由 tmux 或 herdr 满足；Desktop 的批准范围按 spike 结果分为两种结局，都在 PRD 中预先写明。（H7、Q2）
21. **DS21 — 配置可逆与 notify 链式包装**：安装前备份，卸载后逐字节还原；守护进程不在线时，notify 包装器仍然执行原命令。（F34）
22. **DS22 — 签字前的 5 分钟核查**：herdr 在 macOS 上是否可用（只读查看）；如果不可用，herdr 模式降级为 P1，在模式循环中显示为灰色。（F32、D9）
23. **DS23 — 过期可见**：守护进程退出或 Mac 睡眠时推送 offline 帧；副屏心跳点每 2s 翻转一次。（F13）
24. **DS24 — §9 增加 AC1–AC15**（第 3 节），作为实现阶段的验收基线。
